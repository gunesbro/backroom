# Email (cell)

Contract: [docs/contracts/phase-1.md](../../../../docs/contracts/phase-1.md), safeguards [docs/adr/0008](../../../../docs/adr/0008-email-safety-outside-production.md). Technical module. **Human review required** for every change in this module.

## Responsibility

- `IEmailSender` (provider interface) and its adapters; the only module allowed to use SMTP (architecture test).
- Hard-coded safeguard: outside Production every message goes to Mailpit, whatever the configuration or an organization's own SMTP setting; real sending needs Production **and** the explicit "allow real sending" setting; outside Production the service refuses to start if the SMTP target is not Mailpit; if Mailpit is down, messages wait or fail and are never rerouted.
- Templates in Turkish and English with a version number; Phase 1 template: invitation.
- Delivery log without content, kept 90 days.

## Owns

- Schema `email`: `deliveries`, `inbox`.

## Consumes / depends on

- `organization.invitation-ready.v1` (worker role), published only after the control plane registered that `code_version`; skipped if a newer version exists; the link comes from `IInvitationLinks.GetLinkAsync(invitationId, codeVersion)` (Organization.Contracts) and carries the code in the URL fragment.
- Sender name and subject come from fixed templates (`"<organization> on Backroom"`), CR/LF stripped; the organization name is HTML-encoded, length-limited and never turned into a link; no inviter name (product decision); the invitation link is the only link and points to our web origin; the email says what to do if the invitation was unexpected.

## Rules

- Never log message content, recipient addresses, links or invitation codes; recipients are stored as hashes.
- Tests read mail through the Mailpit API and use `.test` addresses.

## Status

- Implemented: projects `Email.Application` (`IEmailSender`, `EmailMessage`, `EmailDispatcher`, the delivery log interface, templates, the invitation consumer) and `Email.Infrastructure` (MailKit adapter, options, migrations); wired into the cell's worker role only. No Contracts project yet (no other module calls Email). Depends on Organization.Contracts.
- Settings (`Email` section): `FromAddress`, `FromName`, `RecipientHashKey` (secret, base64 of at least 32 bytes), `Mailpit:Host`/`Port`, and only for real sending `AllowRealSending` and `Smtp:Host`/`Port`/`Security` (`StartTls` or `Tls`; no plain text)/`UserName`/`Password` (secret). Validated at startup.
- Real sending iff the environment is Production **and** `AllowRealSending` is on (`EmailTransport.Resolve`, the only place that picks the server). Otherwise Mailpit, even in Production. Outside Production the worker does not start if `AllowRealSending` is on or any `Smtp` value is set. Real sending also needs the environment name set explicitly (`DOTNET_ENVIRONMENT`/`ASPNETCORE_ENVIRONMENT`), because .NET reports Production when none is set. At startup the worker logs where email goes and warns when `Smtp` is configured but real sending is off.
- "Is Mailpit" (`MailpitGuard`): at startup the host must be a loopback address, `localhost` or exactly `mailpit` (no other name, even one containing "mailpit"). On every connection the greeting must be Mailpit's (`220 <host> Mailpit ESMTP Service ready`). MailKit sends `EHLO` (our host name only) before the check; `AUTH`, `MAIL`, `RCPT` and `DATA` come only after it. On a mismatch the connection is closed and the send fails `NotMailpit`. Mailpit down: the send fails `Unavailable`; nothing is rerouted or retried here. An architecture test rejects Mailpit's outbound features (relay, forwarding, webhooks) in sources and deployment files.
- **The host allowlist is the boundary; the greeting check is defence in depth.** Any server can send Mailpit's greeting, so it only catches accidents (a local relay, a misresolved `mailpit` name). Never loosen the allowlist (other names, configurable hosts, wildcards) on the grounds that the greeting is checked.
- Schema `email`: `deliveries` (contract columns only; recipient as HMAC-SHA256 with the cell's key; `provider_message_id` is our own Message-ID; status `pending` → `sent` | `failed` | `unknown`; the application role cannot delete) and the standard `inbox`, both under RLS. `EmailDispatcher` commits the pending row, sends outside any transaction, then commits the outcome.
- Send stages (`SmtpEmailSender`, `GreetingRecorder.HandoverStarted`, set when the client writes `DATA` or `BDAT`): before the hand-over a broken connection is `Unavailable` and a shutdown `Cancelled` (the row becomes `failed`, then `OperationCanceledException` is thrown, so a redelivery sends); an SMTP error reply is `Rejected` at any stage; a broken connection, timeout or shutdown after the hand-over, before the reply, is `Unknown` (the row stays `pending`, never retried); once the server accepted the message it is `sent`, whatever happens during `QUIT`.
- **A row left `pending` means the outcome is unknown**: the connection broke or the send was cancelled after the hand-over, or the server accepted the message and the outcome commit then failed. Never resend a stale `pending` row blindly; that would send a second invitation. Retries go through the event's redelivery and inbox (at most one send per invitation and `code_version`). The maintenance job `email.delivery-stale-pending` (every 5 minutes, batches of 250) closes a `pending` row whose `updated_at` is older than one hour (far above the 30 s send timeout) as `unknown`, never as `failed` and never resent. Why not `failed`: the unique index lets a new row in once all rows of a reference are `failed`, and if the event's transaction was lost after the hand-over (a crash) the inbox has no record of it, so a redelivery after a long outage or a dead-letter replay would send a second invitation. `unknown` is not `failed`, so the index (`status <> 'failed'`) and the `ON CONFLICT` predicate keep blocking it.
- Delivery reference: `reference_id`/`reference_version` (ids only; for invitations the invitation id and `code_version`) with the partial unique index `deliveries_reference_once_idx` on `(org_id, template, reference_id, reference_version)` where the status is not `failed`. `EmailDispatcher.SendOnceAsync` inserts the pending row with `ON CONFLICT DO NOTHING` and sends nothing if a delivery for that reference is already `pending` or `sent`; a `failed` one stays as history and does not block a retry.
- Invitation email (`InvitationReadyConsumer`, inbox `email.inbox`): reads the link through `IInvitationLinks.GetLinkAsync` in the event's unit of work (null → nothing sent, logged with ids), renders template `invitation` v1 and sends it with `SendOnceAsync`. Redelivery is stopped twice: by the inbox, and by the delivery reference if the event's transaction was lost after the send. Only `Unavailable` throws, so the event's retries (5 s, 30 s, 2 min, 10 min, then the dead-letter queue) try again; `Cancelled` returns the event to its queue; `Rejected` and `NotMailpit` are recorded as `failed`, `Unknown` stays `pending`, and none of them is retried. **This is the one handler that makes an external call while the event's transaction is open** (the building block's rule otherwise forbids it): the dispatcher records the delivery in its own transactions, so the outcome survives a rollback; the open transaction holds one pooled connection per queue (one delivery at a time) for at most the send timeout. Bulk email needs a send queue instead.
- Templates (`Templates/`): texts in embedded translation files `invitation-v1-en.json` and `invitation-v1-tr.json` (same keys; `{organization}` and `{product}` placeholders, product first so a name cannot expand one); the event's `locale` picks the language, English for anything but Turkish. Invitations are always `en-US` for now (product decision); the Turkish texts are ready for later. The product name is `EmailBranding.ProductName` (the code name "Backroom"), one constant for the later rename. Names go through `EmailText.CleanName` (control characters and line breaks become spaces; format characters such as direction overrides, zero-width spaces, soft hyphens and BOMs are removed, except a zero-width joiner or non-joiner between two letters, marks or symbols, which Persian, Indic scripts and emoji sequences need; at most 60 characters without splitting one) and `EmailText.WithoutLinks` (a word joiner after `.`, `@`, `:` and `/`, so clients do not link a name that looks like an address). In the sender name and subject (`EmailText.HeaderName`) `@` also becomes a space, so `security@bank.example` cannot pass for an address; without a visible name the sender name has its own text (`unnamedSenderName`). Every HTML text is encoded. **Not handled: look-alike letters (homoglyphs such as Cyrillic "а" for Latin "a") and right-to-left letters.** Catching homoglyphs needs the Unicode confusables data (UTS #39) and would garble legitimate names in other scripts, and right-to-left letters are real names, not tricks (only the direction overrides are, and they are removed). The risk is bounded: the sender address is always our fixed address, the name is the organization's own, the link goes only to our web origin, and the sending limits apply. Plain-text and HTML parts; the link is the only `href` and also shown as text to copy. Bump the template version whenever texts or layout change.
- One SMTP connection per message (connect, `EHLO`, send, `QUIT`, 30 s timeout per operation): simple and isolated, and enough for invitation volumes, which the daily limits bound. Bulk sends (digests, notifications) need a pooled or pipelined connection, or a provider API adapter, and a measurement before they are added.
- Logs and spans (`Backroom.Email`) carry delivery, organization and template ids, status and failure kind only; SMTP failures are logged by status code or exception type, never by server text.
- Maintenance jobs (worker role, `AddMaintenanceJob`, run as `backroom_maintenance`, docs/adr/0010, migration `20261124110000_AddDeliveryMaintenance`): `email.delivery-stale-pending` (above) and `email.delivery-retention` (every hour, batches of 250, deletes rows 90 days after `created_at` whatever the status; `email.deliveries` has no foreign keys, so nothing cascades). Both use `FOR UPDATE SKIP LOCKED` and report their backlog. The role has `SELECT` only of `id, status, created_at, updated_at` (never `recipient_hash`, `provider_message_id` or the reference), `UPDATE` of `status, updated_at` and `DELETE`.
- Not yet: the block list, per-organization providers, delivery status for admins (Phase 2; the delivery reference finds an invitation's delivery).
