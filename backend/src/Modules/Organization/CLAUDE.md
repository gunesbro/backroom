# Organization (cell)

Contract: [docs/contracts/phase-1.md](../../../../docs/contracts/phase-1.md) (flows 2 and 3, "Invitation security"). **Human review required** for membership and invitation logic.

## Responsibility

- Organizations in this cell, created only through `IOrganizationProvisioning.ProvisionAsync` (idempotent by organization id). In the same transaction it calls `IPermissionsProvisioning` to create the system roles and assign Owner.
- Members: organization-specific profile (display name, email, locale), status, version (incremented on every change). Removing, deactivating or demoting a member revokes their pending invitations in the same transaction.
- Invitations (contract flow 3):
  - create: `members.invite-by-email`; email is exactly one address (no CR/LF, commas, display names; ASCII local part; ≤ 254 chars; IDN → punycode with ICU; trim, NFC, `ToLowerInvariant`); `role` only with `members.choose-role-on-invite`, never Owner, a subset of the inviter's permissions; default Member;
  - reject active (`organization.already_member`) and deactivated (`organization.member_deactivated`) members; a new invitation to the same email revokes the pending one if the caller is its inviter or holds `members.manage-invitations`, otherwise `409 organization.invitation_pending`;
  - attempts: 100 per account and organization per day, refused ones included (in-memory sliding window per instance);
  - limits: 50 per inviter and 200 per organization per day, 3 per recipient address per day in the organization (resends included), 500 pending per organization;
  - code `base64url(HMAC-SHA256(key[v], invitation_id ‖ salt))`, 128-bit salt, always the current key version; resend makes a new salt and increments `code_version`; only `SHA-256(code)` is stored; the code is never logged or put in an event;
  - key compromise: revoke every pending invitation of that key version, re-issue each under the current key (new salt, new `code_version`, new email), then delete the version;
  - states `pending` → `accepted` | `revoked` | `expired`; the expiry job runs 24 hours after `expires_at` so late-delivered acceptances still succeed; email and personal data of expired and revoked invitations are deleted after 30 days.
- `IInvitationLinks` (Organization.Contracts): `GetLinkAsync(invitationId, codeVersion)` for Email (null unless that version is current and registered with the control plane, and the invitation pending and unexpired), `GetCodeHashAsync(invitationId, codeVersion)` for ControlPlaneConnector (null unless that version is current and the invitation pending and unexpired).
- `IInvitationRegistration.MarkRegisteredAsync(invitationId, codeVersion)` (Organization.Contracts): called when the control plane acknowledged `InvitationRegistered` for that `code_version`; publishes `organization.invitation-ready.v1` (locale `en-US`) only if it is still the current version, not yet recorded, and the invitation pending and unexpired, so a repeated acknowledgement sends no second email.
- `IInvitationAcceptance.AcceptAsync` (Organization.Contracts) for `InvitationAccepted`, in one transaction: conditional update on `accepted_at IS NULL AND revoked_at IS NULL`; `accepted_at ≤ expires_at + 60 s` using the control plane's time; the event's email equals the stored email; the inviter is still active and may still grant the role; the person is not deactivated; then add the member and assign the role through `IPermissionsProvisioning`. Already an active member → mark the invitation `accepted`, no other change. Business rejections → non-retryable `Nack`: `organization.invitation_not_pending`, `invitation_expired`, `invitation_email_mismatch`, `inviter_not_authorized`, `member_deactivated`.
- `IMembershipQueries` (Organization.Contracts): `IsActiveMemberAsync` for the organization context, membership snapshot and digest.
- Endpoints: `GET /api/v1/orgs/{orgId}`, `GET /api/v1/orgs/{orgId}/members` (display names only; email only for the caller), `POST`/`GET /api/v1/orgs/{orgId}/invitations` (list: all with `members.manage-invitations`, otherwise own), `DELETE .../invitations/{id}` (inviter or `members.manage-invitations`; `409` once accepted), `POST .../invitations/{id}/resend` (pending only; inviter still holding `members.invite-by-email`, or `members.manage-invitations`).

## Owns

- Schema `organization`: `organizations`, `members`, `invitations`, `invitation_resends`, `outbox`.

## Publishes

- `organization.member-added.v1`, `organization.member-removed.v1`, `organization.invitation-created.v1` (also on resend), `organization.invitation-ready.v1`, `organization.invitation-revoked.v1`. None carries the code.

## Rules

- Every table has `org_id` and RLS.
- This module never touches messaging data; no role can read other people's messages.

## Status

- Implemented: schema `organization` with `organizations` (`org_id = id`, so the organization policy applies) and `members`, both under RLS; `IOrganizationProvisioning.ProvisionAsync` (Organization.Contracts) creates the organization, the owner as first active member (version 1), and through `IPermissionsProvisioning` the system roles with Owner assigned, in the caller's unit of work; idempotent by organization id (another owner → `organization.exists`); values checked against the column limits (`organization.provisioning_invalid`). Called by ControlPlaneConnector for `OrganizationProvisioned`.
- Membership check and reads: `InOrganization()` (BuildingBlocks.Presentation) gives every `{orgId}` endpoint a signed-in account, the route's organization, the unit of work and `IOrganizationMembershipCheck` (implemented here, `status = 'active'`), in that order; every failure answers the same `404 organization.not_found`. `GET /api/v1/orgs/{orgId}` and `/members` (keyset by account id, at most 100; other people's emails are not read from the database). Access ends with the membership, not with the token.
- Invitations, create and list (`AddOrganizationInvitations`, endpoints behind the flag `Features:Invitations`, off by default until the whole flow exists): table `organization.invitations` and the module's `outbox`, both under RLS. `POST /invitations` checks, before any write: the email (`EmailAddress`, BuildingBlocks.Domain, shared with the control plane), the role (a given role needs `members.choose-role-on-invite` and must be `admin` or `member`; the role, the default included, must be one the inviter can grant), members with that email (`members.email_key`, a generated column `lower(email COLLATE "C")` with an index; member emails with a Unicode domain or non-NFC text do not match an invited address, and acceptance's "already a member" path covers them), whether someone else's pending invitation is in the way, and the limits; it then revokes the pending invitation to that email (`organization.invitation-revoked.v1`), stores the new one and publishes `organization.invitation-created.v1`. Creation takes a row lock on the organization (`FOR NO KEY UPDATE`, `lock_timeout` 5 s, fails if no row was locked); every later write to invitations (revoke, resend, acceptance) must take that lock first so the lock order stays the same. So the limits and "one pending per email" (also a unique partial index) hold under concurrency. `GET /invitations` is keyset-paged by id, at most 100.
- Codes: `InvitationCode` derives `base64url(HMAC-SHA256(key, id ‖ salt))` (id in network byte order, 43 characters); the stored hash is SHA-256 over those characters. Keys come from `Organization:InvitationKeys` (`CurrentVersion`, `Keys:{version}` as base64 of at least 32 bytes), validated at startup in every role. Creating an invitation computes the code only to hash it.
- Limits are rolling 24-hour windows counted from the invitations table; `Retry-After` is when every exceeded limit has cleared (one hour for the pending cap). The per-recipient limit (3 a day) is counted inside the organization, as the contract says: a cell-wide count would need a read that row-level security does not allow, and would tell one organization that another invited the same address.
- Revoke and resend (`InvitationManagement`, same flag): `DELETE .../invitations/{id}` and `POST .../invitations/{id}/resend`, for the inviter or a member with `members.manage-invitations`; anyone else gets `404 organization.invitation_not_found`, like an unknown id (the same queries run either way). Who may act is decided before the organization lock, so other members cannot hold it up; the lock is taken before the invitation row is read again and changed. Revoke publishes `organization.invitation-revoked.v1`. Resend checks that the inviter is still an active member who holds `members.invite-by-email` and can grant the role (an inviter resending their own gets `403`, a manager `409 organization.inviter_not_authorized`) and that a manager resending can grant it too, refuses expired invitations, issues a new salt under the current key with `code_version + 1` (clearing `registered_at`), keeps the expiry, records a row in `invitation_resends` and publishes `organization.invitation-created.v1` with the new version. `InvitationSendLimits` counts new invitations and resends as sends for all three daily limits.
- Registration with the control plane (same `AddOrganizationInvitations`): `IInvitationLinks.GetCodeHashAsync` (hex of the stored hash) and `IInvitationRegistration.MarkRegisteredAsync`, which takes the organization lock, sets `registered_at` with one conditional update and publishes `organization.invitation-ready.v1` (`invitation_id`, `code_version`, `locale`: always `en-US`, so the cell never learns whether the invited address has an account). It publishes nothing if the inviter is no longer an active member who may invite into the role, since acceptance would refuse it (until removal revokes their invitations, such an invitation stays pending without an email). The connector calls `GetCodeHashAsync` from its `invitation-created.v1` consumer and `MarkRegisteredAsync` when the control plane acknowledges the registration. The worker's relay publishes this module's outbox (`AddOrganizationInvitations` adds the schema to `OutboxRelayOptions`).
- Links for the invitation email: `IInvitationLinks.GetLinkAsync(invitationId, codeVersion)` returns an `InvitationLink` (URL, invited address, organization name; its `ToString` shows none of them) or `null`. One primary-key read joins `organizations` (row-level security on both) and requires `pending`, that `code_version`, `registered_at` set (a re-issue clears it, so the link already resolves upstream) and `expires_at` ahead. `InvitationLinkBuilder` derives the code again with the stored salt and that key version (`InvitationKeyRing.KeyOf`), checks `SHA-256(code)` against the stored hash in constant time (a missing key version or a mismatch gives `null` and an error log with ids and the key version only), and builds `<web origin>/invite#<code>`; the code bytes and the salt are cleared, the link string lives only while the email is sent. The web origin is `Organization:InvitationLinks:WebOrigin` (`AddOrganizationInvitationLinks`, worker only, validated at startup: https, or http on a loopback host in Development; origin only, no path, query, fragment or user information); the AppHost sets the web dev server `http://localhost:5173`.
- Acceptance (same `AddOrganizationInvitations`): `IInvitationAcceptance.AcceptAsync(AcceptedInvitation)`, called by the connector for `InvitationAccepted`. It bounds the values by the member columns and refuses an `accepted_at` more than 60 s ahead of the cell's clock (`organization.invitation_acceptance_invalid`), reads the invitation once before the organization lock (unknown in this organization, or an organization this cell does not have: `NotFound` `organization.invitation_not_found`, which the connector answers with a retryable `Nack`), then under the lock reads it again and checks, in this order: still `pending`; `accepted_at ≤ expires_at + 60 s` (the message's time); the message's email, normalized with `EmailAddress`, equals the stored one; the account's membership (active → only the invitation is marked `accepted`, no role or event, whatever the inviter's rights now; deactivated → `organization.member_deactivated`); the inviter is still an active member with `members.invite-by-email` who can grant the role (`InviterAuthorization`). Then one conditional update marks the invitation `accepted` (`accepted_at` from the message, `accepted_by`), `IMemberStore.JoinAsync` adds the member (version 1) or makes a removed one active again with the new profile (version + 1), `IPermissionsProvisioning` gives the invited role (for a rejoining member, version > 1, `RemoveMemberAsync` first clears every role left from before, so only the invited one remains), and `organization.member-added.v1` (`org_id`, `account_id`, `role`, `version`; no name or email) goes into the outbox, all in the connector's unit of work. Accepted, already-member and refused acceptances are security log events with ids and the code only.
- Not yet: `organization.member-added.v1` for organization owners (organizations provisioned emit no event for their owner, and the membership digest repairs the control plane's view); nobody consumes `member-added.v1` until the connector's membership consumers exist. For invitations: revoking a member's invitations when they lose the right to invite. Before the flag goes on: a registration given up after 50 link attempts (`delivery_expired`, logged as an error) leaves its invitation pending without an email; `invitation_resends` rows (account ids) are kept beyond the 30 days the contract allows (the retention job deletes only the invited email so far).
- Scheduled jobs (`InvitationExpiryJob` `organization.invitation-expiry` and `InvitationRetentionJob` `organization.invitation-retention`, worker role only, `AddOrganizationInvitationJobs`, run by the host's `AddMaintenanceJobRunner`, docs/adr/0010): a pending invitation becomes `expired` (sets `expired_at`, no event, security log with ids only) 24 hours after `expires_at`; the invited email of `expired` and `revoked` invitations is set to NULL (and `email_erased_at` to the time of the erasure) 30 days after `expired_at` or `revoked_at`. Batches of 250 with `FOR UPDATE SKIP LOCKED` (own transaction each, run by the building block), every 5 minutes, served by the partial indexes of `20261115150000_IndexInvitationJobs` as redefined by `20261124100000_EraseInvitationEmailsByMarker` (retention filters on `email_erased_at IS NULL`, never on `email`). Both jobs report their backlog (`IMaintenanceBacklog`). They work across organizations as the maintenance role (`MaintenanceJobs:ConnectionString`, BYPASSRLS, owns nothing); that migration grants it column privileges only: `SELECT` of `id, org_id, status, expires_at, expired_at, revoked_at, email_erased_at` (never `email`, the code hash or the salt) and `UPDATE` of `status, expired_at, email, email_erased_at`, and revokes every invitation privilege from the relay role. No organization context is set.
