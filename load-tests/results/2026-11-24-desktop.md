# First load test run: desktop, 2026-11-24

The first real run of the `messaging` and `catch-up` scenarios: a small smoke run on a desktop, not the 5,000-user target.

The performance budget is defined for a 4-core, 8 GB laptop (CLAUDE.md, "Performance and resources"). This machine is far stronger (8 cores, 16 threads, 31 GB), so these numbers are not a budget verdict for that class of machine; a run on budget-class hardware is still needed.

## Findings

### The send tail is PostgreSQL commit latency on Docker Desktop's disk

`send_ms` is bimodal: the median is 8.6 ms, but about 5 % of sends take 300 to 700 ms, at any rate (2, 10 and 30 sends/s all show it) and with or without listeners. Reads never do (max 10 ms). `message_visible_ms` inherits the tail, because the stamp is taken before the send.

- `pgbench` (TPC-B, 10 transactions/s) inside the run's PostgreSQL container: 1.5 % of transactions above 50 ms and 1 % above 400 ms, while `SELECT 1` stays at 0.25 ms. The commit's WAL flush (`fdatasync`) on the container's disk stalls now and then.
- A/B: with `synchronous_commit = off` on the isolated server only (reset afterwards), the same load (40 listeners, 10 sends/s) gave `send_ms` p95 7.8 ms (max 12 ms) and `message_visible_ms` p95 8 ms (max 14 ms).

So the tail comes from the environment (an unpersisted container layer on the WSL 2 disk, shared with another running stack), not from the send path. The send path itself is fast: one row lock per channel for the sequence number, one insert, one outbox row, one commit. Budget numbers need a stack with a proper disk; do not turn off `synchronous_commit` to meet them, because an acknowledged message must survive a crash.

### One failed catch-up request: caused by the test operator

The single failed request in the first `catch-up` run came seconds after PostgreSQL restarted through crash recovery: a stray `createdb` from the `pgbench` check was killed inside the container, and PostgreSQL (PID 1) treats an untracked child that dies as a crash. Connections in the cell's pool were terminated; the first use of one fails. Three later runs had no failures. Not a product bug; whether a request that lands on a connection killed by a database restart should be retried is a resilience question for later.

### No product errors

No 5xx, no refused subscriptions, no token refresh failures (the token server refreshed 40 chains every 150 s without a failure for the whole session).

## Script fixes made for this run

- `lib/signalr.js`: the hub answers the MessagePack handshake in a binary frame, so the client never subscribed and `message_visible_ms` had no samples. The first frame is now read as the handshake answer whatever its type. Subscriptions carry an invocation id and count as ready only when the server completes them (a refused one counts as a `ws_errors`); pings stop once the socket is closed.
- `scenarios/messaging.js`: the listener's `sleep(1)` blocked the VU's event loop, so every socket callback, and `ws_ready_ms`, came exactly one second late. A timer now keeps the iteration alive instead.
- `tools/loadtest.mjs cleanup`: reported 10 of 40 deleted users although all 40 were gone (`deleted += await ...` lost concurrent updates).

k6 v2.4.0 needed no other changes; the fixture path, token refresh and `k6 inspect` worked as written.
