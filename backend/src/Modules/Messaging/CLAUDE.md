# Messaging (cell)

Contracts: [docs/contracts/phase-1.md](../../../../docs/contracts/phase-1.md) (flow 4), [docs/contracts/phase-2.md](../../../../docs/contracts/phase-2.md) (Phase 2, in progress).

## Responsibility (Phase 1 core)

- Public channels: create, list.
- Plain-text messages in channels: send (idempotent by `clientMessageId`), list with keyset pagination (`before`, `after`, `limit`; `after` serves reconnect catch-up).
- Storage model: the server validates the text (plain text, NFC, 1 to 4,000 characters, never HTML-escaped) and derives the structured blocks (`[{ type: "paragraph", children: [{ type: "text", text }] }]`, plain strings; later rich text adds marks, mention nodes and list, quote and code block types); client-supplied blocks are not accepted. Escaping happens at render time in the clients. Each message gets a per-channel sequence number `seq` (commit order). Mentions table and the rich text editor arrive in Phase 2.
- Phase 2 adds DMs, group DMs, private channels, threads, replies, forwarding, reactions, read state, polls, scheduled messages, reminders, link previews.

## Owns

- Schema `messaging`: `conversations` (Phase 1 `channels`), `conversation_members`, `messages`, `outbox`. No table is added by private channels (step 7).

## Publishes / depends on

- Integration event `messaging.message-posted.v1` (no text).
- Live events through `ILiveEventPublisher` (Realtime.Contracts) after commit: `MessagePosted` (`MessagePosted.v2` with `Features:MessageSync`) to the conversation group, `ChannelCreated` to the organization group; a leave asks Realtime to take the account's connections out of the conversation group (`RemoveFromConversationAsync`; the outbox event repeats it durably).
- `IPermissionChecker` (Permissions.Contracts); membership comes from the organization context.
- `ICellEpoch` (BuildingBlocks.Application): the cell's confirmed epoch, registered by `AddCellEpochFence` (control plane connector).
- Integration events `messaging.conversation-created.v1`, `messaging.conversation-changed.v1`, `messaging.conversation-member-added.v1`, `messaging.conversation-member-removed.v1` (ids, the kind and a member count only; never a name).
- Publishes `IConversationReadAccess` (Contracts): whether an account may read a conversation (an open public channel, or an open conversation it is a member of), used by Realtime's subscription check, and `IsMemberAsync` (an open membership), used by Realtime's late-removal check.
- Publishes `IMessageFileAccess` (Contracts): whether an account may read a message that carries a file, asked by Files on every download of an attached file. Until attachments (Phase 2 step 22) no message carries files, so it answers false.

## Rules

- Message content is never logged and never leaves the cell.
- Every table has `org_id` and RLS.
- Message ids are UUIDv7 and give the ordering.

## Status

- Implemented (Phase 1 step 6.1): projects Application, Contracts, Infrastructure, Presentation; schema `messaging` with `channels`, `messages` and `outbox`, all under RLS (migration `20261124120000_CreateChannelsAndMessages`). Queries are hand-written Npgsql SQL in the request's unit of work, like Organization.
- Channels: `POST`/`GET /api/v1/orgs/{orgId}/channels`. Create needs `channels.create-public`; both need membership (outsiders get `404 organization.not_found`). Names follow Directory's `DisplayText` rule (mirrored in `DisplayText.cs`: NFC, trimmed, at most 80 user-perceived characters, a visible character, no control or format characters except ZWNJ/ZWJ between characters); unique among open channels per organization by `name_key` (`ToLowerInvariant`, never the current culture), else `409 messaging.channel_name_taken`. The list is keyset by id, oldest first, page size 1 to 100 (default 50).
- Messages: `POST .../conversations/{conversationId}/messages { clientMessageId, text }` (needs an open membership: `403 messaging.not_a_member`) and `GET ...?before=&after=&limit=` answering `{ items, next }`; the Phase 1 `channels/{id}/messages` routes are removed; `GET .../conversations` lists the caller's open memberships (`{ items, next }`, newest message first by `(last_message_at DESC, id DESC)`, creation time when there is no message; `next` is an opaque cursor, a malformed one is `400 messaging.cursor_invalid`; migration `20261125090000_AddConversationLastMessageAt` adds `last_message_at`, set by every send). `text` is stored raw and validated (see the storage model), `blocks` derived. In the send transaction `UPDATE conversations SET last_seq = last_seq + 1, last_message_at = now RETURNING last_seq` (`change_seq` since Phase 2 step 5, see below) takes the channel row lock until commit, so `messages.seq` order is commit order (ids are assigned before the commit, so id order is not); sends to one channel are serialized to their commit, and `seq` has gaps. Sending is idempotent through the unique index `(channel_id, author_account_id, client_message_id)` (the repeat check relies on READ COMMITTED, checked by a test): a repeat answers `200` with the stored message and publishes nothing. The message row and the `messaging.message-posted.v1` outbox row (ids only) are written in one transaction; `messages (org_id, channel_id)` is a composite foreign key to `channels (org_id, id)`. Reads page by `seq`: `after` gives oldest first (catch-up, resume with `after={lastSeenSeq}`), otherwise newest first (`before` pages back); `next` is the cursor for the following page or `null`; `before` with `after` is refused (`messaging.page_invalid`); an unknown, archived or other organization channel is `404 messaging.conversation_not_found`.
- Live events: `AfterCommitLiveEvents` holds `MessagePosted` and `ChannelCreated` until the unit of work has committed; the endpoint filter `PublishLiveEventsAfterCommit` (added before `InOrganization()` so it wraps the commit) flushes them only for a successful response. A publish failure is logged with ids and the exception type, never the payload, and never fails the request.
- Live events are delivered by Realtime's `ValkeyLiveEventPublisher` (step 6.2); `IConversationReadAccess` (Contracts) answers Realtime's channel subscription check.
- Not yet: archiving channels (the column and the filters exist); the feature flag (the endpoints are live behind authentication and membership).

## Phase 2 step 1: conversations schema (human review)

- Migration `20261124150000_RenameChannelsToConversations`: `channels` → `conversations` in place (ids, names, `last_seq` and the RLS policy kept; `last_seq` and its assignment are unchanged, ADR 0012 owns them), with `kind` (`public_channel`, `private_channel`, `dm`, `group_dm`, `thread`; existing rows `public_channel`), `member_count`, and a name only for channel kinds; `messages.channel_id` → `conversation_id`. Name uniqueness (`conversations_public_name_key_idx`) covers open public channels only, so no answer reveals a private channel's name. New `conversation_members (org_id, conversation_id, account_id, role owner|member, joined_at, joined_seq, added_by, left_at)` under RLS, primary key `(conversation_id, account_id)` and partial index `(org_id, account_id, conversation_id) WHERE left_at IS NULL`; Phase 1 creators and authors were backfilled as members at the channel's `last_seq`. The data steps run through `OrganizationDataSql` (docs/adr/0005, data migrations), because the migrator owns the tables but would see no rows under forced row-level security. `Down()` restores Phase 1 and refuses while any non-public conversation exists.
- Read access (`ConversationAccess.CanRead`, `IConversationReadAccess`): an open public channel for every active member, otherwise an open membership; threads and archived conversations are refused until their steps (thread: parent's access; archive: read-only but readable). Phase 1's channel routes use the same check, so a private conversation is `404` for non-members, Owner and Admin included; posting to a public channel still needs no join on those routes.
- Creating a channel makes the creator a member (`joined_seq` 0) and writes `conversation-created` and `conversation-member-added` to the outbox.
- `POST /api/v1/orgs/{orgId}/conversations/{id}/join` (open public channels; a member gets `204` without a change; archived `409 messaging.conversation_archived`) and `/leave` (any member; DMs `409 messaging.cannot_leave_dm`; not a member `204`); unreadable, unknown and foreign conversations are the same `404 messaging.conversation_not_found`. At most 10,000 open memberships per person (`409 messaging.membership_limit`; concurrent joins can exceed it by their number). Membership and `member_count` change in one statement; lock order membership row, then conversation row.
- Ownership transfer when a private channel's owner leaves arrived with step 7 (below), which also changed the lock order to conversation row first.

## Phase 2 step 5: change sequences, tombstones, `changed_after`, cell epoch

- Migration `20261125120000_AddChangeSequences`: `conversations.last_seq` → `change_seq` (every change takes the next number) plus `last_message_seq` (the newest message's `seq`; backfilled from the messages, because a lost idempotent race can leave `change_seq` ahead); `messages.version_seq` (the number of the message's latest change; backfilled to `seq`) with index `messages_conversation_version_seq_idx (conversation_id, version_seq)`; `text` and `blocks` nullable, with `messages_tombstone_check`: they are null exactly when `deleted_at` is set. One backfill statement per table (the helper's lock lasts for the whole migration, so batches would not shorten it); lock waits 5 s, statements 10 min. **Acceptable only before release:** it rewrites the whole `messages` table and builds the index under `ACCESS EXCLUSIVE`, stalling every read and send for its run. Later migrations of large tables backfill in batches outside the lock, add constraints as `CHECK … NOT VALID` followed by `VALIDATE CONSTRAINT`, and build indexes with `CREATE INDEX CONCURRENTLY` in a migration without a transaction. The index is unique: a change number belongs to one message. `Down()` refuses while a tombstone or a changed message exists.
- Send (mechanism unchanged, ADR 0012): the one statement that takes the conversation row lock is now `SET change_seq = change_seq + 1, last_message_seq = change_seq + 1, last_message_at = …  RETURNING change_seq`; the message is inserted with `version_seq = seq`. When a concurrent repeat of the same `clientMessageId` loses at the unique index after taking a number, that number stays unused (a gap) and `last_message_seq` and `last_message_at` are put back from the stored messages under the same row lock (`RestoreLastMessageAsync`, off the normal path), so `last_message_seq` always names a stored message. Lock order is unchanged (membership row, then conversation row). Later changes (edit, delete, reactions, pins, thread summary: steps 9 and later) take the next `change_seq` the same way and write it to the message's `version_seq`, never to `last_message_seq`.
- Tombstones: a deleted message keeps its row and its place in every read (`before`, `after`, `changed_after`). The API answers it with `id`, `seq`, `versionSeq`, `createdAt`, `deletedAt` and null `clientMessageId`, `authorAccountId` and `text`; a repeated send of its `clientMessageId` answers that tombstone and stores nothing. The delete endpoint itself is step 9; the tests delete the way it will. The web's message type still has `text: string` and non-null author and client id: step 9 must make the web handle tombstones before any delete can happen.
- `GET .../messages?epoch=&before=&after=&changed_after=&limit=`: `changed_after={n}` returns the messages with `version_seq > n` in `version_seq` order (new, edited, tombstones), `next` is the following `changed_after`; at most one of the three cursors (`400 messaging.page_invalid`). Every answer carries `epoch` (the cell's confirmed epoch as a string) and items carry `versionSeq` and `deletedAt`; the send answer carries `epoch` too.
- `409 messaging.resync_required`: a presented `epoch` that is not the current one (also without a cursor), a missing `epoch` with `changed_after`, and a cursor ahead of the conversation's `change_seq` (`before` may be `change_seq + 1`). Read access is checked first, so an unreadable or foreign conversation is `404` whatever the cursor says.
- Flag `Features:MessageSync` (off by default, not in the contract's flag list; read once at start, `MessageSync`): on, `before` and `after` also need `epoch`, and a send announces `MessagePosted.v2` (`orgId, conversationId, message { id, seq, versionSeq, kind, clientMessageId, authorAccountId, text, createdAt }, changeSeq, epoch`) instead of `MessagePosted`. It stays off until the web and desktop clients send the epoch, listen to the new event and resync on `409` (step 15, the sync client); then it is turned on and removed.
- The epoch comes from `ICellEpoch` (BuildingBlocks.Application, implemented by the control plane connector's cached gate, so the send path runs no statement for it). While no epoch is confirmed, message reads and sends answer `503 cell.epoch_unconfirmed` (reads too: no number can be handed out without its epoch).
- Left for later steps: `blocks`, `threadId`, `replyTo`, `forward` and `attachments` in `MessagePosted.v2` (steps 6, 9, 13, 22); the clients' side of the epoch (stored epoch, `epoch` on requests, full resync on `409`, `MessagePosted.v2`) and turning the flag on; `historyBoundary` (plan limits); the partial index `(conversation_id, seq) WHERE deleted_at IS NULL` for unread counts (step 11); the epoch on read state, `sync` and the other live events, which arrive with their steps.

## Phase 2 step 7: private channels and channel management (human review)

- Migration `20261125150000_AddPrivateChannels`: `conversations.description` and `owner_account_id` (only a private channel has one), `conversations_private_open_idx` (the admins' count), `conversations_creator_idx` and `conversation_members_added_by_idx` (the hourly brakes). No new table and no data step. The indexes are built under the migration's lock (fine only before release).
- **Who sees what.** `ConversationDetails.IsVisible`: a public channel, or a conversation the account is an open member of. Every conversation route answers `404 messaging.conversation_not_found` otherwise, before any other check, so an Owner or Admin without membership gets the answer of a conversation that does not exist (`PrivateChannel_ForOwnerAndAdminWithoutMembership_IsNotFoundOnEveryRouteAsync` walks every route and compares the bodies). Private channel management belongs to the channel's owner; no permission key is asked for it.
- **Create.** `POST .../channels { name, private?, description?, memberAccountIds? }`: `channels.create-private` or `channels.create-public`, checked in the service because it depends on the body. The creator is the owner (member row `role = owner`, copied to `owner_account_id`); up to 50 other active members join in one statement (also for a public channel). A private channel is never compared with any name and is not announced to the organization: its members get `MembershipChanged` on their own account groups, the outbox gets ids only.
- **Members.** `GET .../conversations/{id}/members` (keyset by account id), `POST .../members { accountIds }` (private channels: any member, 1 to 50 active organization members, people already in it are skipped; a group DM answers `409 messaging.group_dm_add_creates_new`, other kinds `409 messaging.not_a_private_channel`), `DELETE .../members/{accountId}` (the owner; oneself is leaving), `PUT .../owner { accountId }` (the owner, to a member). When the owner leaves, ownership passes to the earliest joined member (ties: lowest account id); when the last member leaves, the private channel is archived (nobody can reach it; a decision of this step, not in the contract).
- **Removal by others is behind `Features:ConversationMemberRemoval`, off by default** (`MemberRemoval`; `403 messaging.member_removal_unavailable`). The contract ("Live events", "Window after the commit"; owner decision 12) does not let removal by others ship until there is a delivery-time membership check or the owner accepts the millisecond window after the commit for it. With the flag on, the removal closes the membership, writes `conversation-member-removed` and calls `RemoveFromConversationAsync` after the commit, like a leave. **The real fix is a membership check at delivery time in the Realtime gateway** (the node checks, before it hands a conversation event to a connection, that the account is still a member), because two windows stay open without it: (1) the group removal runs only after the commit, on its own Valkey subscription, and arrives late when Valkey is slow, so events published meanwhile still reach the removed person's connections; (2) a send that read the sender's or the group's membership before the removal committed still broadcasts to the group afterwards, and nothing at delivery looks at membership again. The flag stays off until that check exists or the owner accepts both windows for removals by others.
- **Manage.** `GET .../conversations/{id}`, `PATCH { name?, description? }` (an empty description removes it; at most 250 characters, `DisplayText` without the visible-character rule), `POST .../archive` and `/unarchive`: `channels.manage-public` for a public channel, the owner for a private one. A public name must be free among open public channels (also on unarchive); the check never looks at private channels. Each change takes the next `change_seq`, so it needs the confirmed epoch (`503 cell.epoch_unconfirmed`), writes `messaging.conversation-changed.v1` (`renamed`, `archived`, `unarchived`, `owner_transferred`; ids, kind and member count, never a name) and sends `ConversationUpdated` to the conversation's group.
- **Admins' view.** `GET .../private-channels/count` (`channels.manage-public`) answers `{ count }`: the open private channels, an index-only count, and nothing else.
- **Locks.** Every membership and management change first locks the conversation row (`IConversationStore.GetAsync(forUpdate: true)`), then touches membership rows; a send takes only the conversation row. The lock and the caller's role are two statements on purpose: under READ COMMITTED a statement that waited for a row lock re-reads only the locked row, so a role joined into the locking statement would be the one from before the wait (review of step 7: an owner and their successor leaving at once left the channel to someone who had left). `SetOwnerSql` writes an owner only when that account holds an open membership. Tests hold the row lock, queue both requests behind it and let go (`RaceAsync`). This replaces step 1's order (membership row first) for join and leave too. The organization-removal consumer (step 30) and group DMs (step 8) must follow it.
- **Brakes** (`ConversationBrakes`, counted from stored rows): 20 new channels and 200 member additions per account, organization and hour, `429 messaging.rate_limited` with `Retry-After`.
- **Live events.** `MembershipChanged { added | removed }` goes to the person's own account group for every opened or closed membership (join, leave, add, remove, create). Every membership or ownership change of an existing conversation (join, leave, add, remove, transfer, succession) also takes the next `change_seq` and sends `ConversationUpdated` with the new `memberCount` to the conversation's group, so clients and sync see it; the payload has no owner field, clients refetch the conversation. `joined_seq` is the `change_seq` before the join's own number. Without a confirmed epoch the membership change still happens and only the live event is left out (a leave or removal is never held back by the control plane link); rename and archive answer `503` instead.
- **Left for later steps:** archived conversations are still unreadable through `ConversationAccess.CanRead` (messages, Files, Realtime, Notifications); the contract wants them readable and read-only, which changes Files' upload check and Realtime's subscription check, so it needs its own PR. The conversation list still leaves archived conversations out. Each added member is one outbox insert (at most 51 per request; `IOutbox` has no batch). Audit consumes the events in step 32; `IConversationNames` arrives with it. Web UI: none in this step.
