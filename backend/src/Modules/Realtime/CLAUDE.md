# Realtime (cell)

Contract: [docs/contracts/phase-1.md](../../../../docs/contracts/phase-1.md) ("Identity and tokens", "Live events"). Technical module (no Domain project; no tables except an inbox).

## Responsibility

- SignalR hub `/hubs/realtime` in the `app` role, MessagePack protocol, Valkey backplane; `CloseOnAuthenticationExpiration` so connections end with their token.
- Groups per conversation (`cell:{cellId}:org:{orgId}:channel:{channelId}`) and per organization for content-free events. `SubscribeOrganization` / `SubscribeChannel` check membership and read access.
- `ILiveEventPublisher` (Realtime.Contracts) for modules, used after commit.
- Revoked sessions: `ISessionRevocation` (Realtime.Contracts) stores the session or account in Valkey until `keep_until`, closes matching connections on all nodes, and backs the authentication check that rejects revoked tokens on HTTP and hub connects.
- Consumes `organization.member-removed.v1` to remove the account's connections from that organization's groups.

## Owns

- Schema `realtime` with only an `inbox` (the `member-removed` consumer). Connection, group and revoked-session state live in SignalR and Valkey.

## Rules

- Live events never go through RabbitMQ and never wait for it.
- Payloads are versioned by event name (`MessagePosted`, later `MessagePosted.v2`), because clients may talk to cells on different versions.
- Message text is in live events but never in logs; the `access_token` query parameter is redacted.

## Status

- Implemented (Phase 1 step 6.2): `Backroom.Modules.Realtime.Contracts` (payloads with MessagePack `[Key("camelCase")]` attributes, `ILiveEventPublisher`, `LiveEventNames`) and `Backroom.Modules.Realtime.Infrastructure` (technical module: hub, gateway and publisher in one project, because the publisher sends through the hub's context; no Presentation project). Schema `realtime` holds only the consumer's `inbox`.
- **Hub** `/hubs/realtime` (`MapRealtimeHub`, app role): authenticated, MessagePack only (`SupportedProtocols = ["messagepack"]`; SignalR always registers the JSON protocol, but the handshake refuses it), `CloseOnAuthenticationExpiration`, explicit limits (`Realtime` options: receive size 4 KB, 200 groups per connection, 20 connections per account per node, keep-alive 15 s, client timeout 30 s, handshake 10 s, one invocation at a time per client, WebSockets only; 60 subscribe calls per 10 s and 10 refused ones per connection, after which the connection is aborted with `realtime.rate_limited` / `realtime.too_many_refusals`). Methods `SubscribeOrganization`/`UnsubscribeOrganization`/`SubscribeChannel`/`UnsubscribeChannel`; refusals are `HubException`s with the stable codes `realtime.not_found` (non-member, other organization, unknown, archived or non-public channel: the same code for all, so nothing leaks), `realtime.invalid_argument`, `realtime.subscription_limit`, `realtime.unavailable`.
- **Checks:** the organization comes from the argument, is entered in the hub invocation's scope and accepted only after `IOrganizationMembershipCheck`; for a channel `IChannelReadAccess` (Messaging.Contracts: open, public in Phase 1) is checked in the same transaction under RLS. The token's `sub` is the account (`AccountUserIdProvider`).
- **Publisher:** `ValkeyLiveEventPublisher` sends to the SignalR group (`cell:{cellId}:org:{orgId}:channel:{channelId}` / `cell:{cellId}:org:{orgId}`); the Valkey backplane (`Microsoft.AspNetCore.SignalR.StackExchangeRedis`) delivers it to connections on every node. Bounded: waits at most `PublishTimeout` (250 ms, because the sending request waits for it; the multiplexer fails fast while Valkey is down), at most `MaxConcurrentPublishes` (256) in flight, further events are dropped (never queued), failures are logged with ids and the exception type and counted, and nothing reaches the caller.
- **Valkey connection:** `ValkeyConnection` (one multiplexer per process, `Valkey:ConnectionString`, `AbortOnConnectFail=false` so the cell starts when Valkey is down) with the pub/sub channel prefix `backroom:cell:{cellId}:` (development cells share one server). The AppHost passes `Valkey__ConnectionString` to the cell's app and worker and pins the image (`ValkeyImageTag`, same as the tests' `ValkeyServer`).
- **Member removal across nodes.** A node only knows its own connection ids, so removal is a broadcast: the worker's `MemberRemovedConsumer` (`organization.member-removed.v1`, inbox in schema `realtime`) publishes the two ids (32 bytes) on the Valkey channel `realtime:member-removed`; every app node's `GroupRemovalListener` receives it and removes its own connections of that account from the groups of that organization (`ConnectionRegistry`: connection → account and groups; state exists only while the connection is open, at most 200 groups per connection and 20 connections per account). The consumer throws when Valkey does not accept the message, so RabbitMQ redelivers; removing twice is harmless. Each connection has a gate held from the membership check to the group join (and by the removal), so a subscribe cannot slip past a removal. Pub/sub is at most once: a node that missed the message keeps the connection in the group only until its token expires (`CloseOnAuthenticationExpiration`, five minutes), and the reconnect has to pass the membership check again. Messages are handled in order, one at a time; they come at the rate of members being removed, so the listener has no queue worth bounding.
- **Token:** the cell's JWT validation (audience `cell-{cellId}`) accepts `access_token` from the query string on the hub path only (`AddAccessTokenAuthentication(..., queryTokenPath)`); elsewhere a token in a URL is refused. The query token is kept out of logs by turning off the hosting `Request starting/finished` lines (`Microsoft.AspNetCore.Hosting.Diagnostics` at Warning, set by the same call) and out of traces by `QueryRedaction` (ServiceDefaults, `url.query` tag). A test captures every log line of a connected client.
- **Metrics** (meter `Backroom.Realtime`): `backroom.realtime.connections`, `.subscriptions`, `.publishes`, `.publish_failures` (tags `event`, `reason`), `.rejected_subscriptions`.
- Tests (`Backroom.Modules.Realtime.IntegrationTests`): two app nodes on one Valkey (Testcontainers), a message posted through node A reaches node B; subscribe checks; member removal on both nodes; token expiry (a token the test signs with a second trusted key, because Keycloak's live for five minutes); JSON refused; limits; no token in logs; publish failure with Valkey down.
- **No producer yet:** `MemberRemovedConsumer` has nothing to consume until Organization publishes `organization.member-removed.v1` when member removal ships.
- **Deploy phase:** Valkey carries the SignalR backplane and the removal channel, so anyone who can reach it can inject live events into any group and make nodes drop subscriptions. It needs ACLs (a user limited to pub/sub and the keys the backplane uses), TLS and network isolation (only the cell's nodes), and the connection string stays a secret.
- Not yet: `ISessionRevocation` and the `SessionRevoked` event (step 6.3), the Organization module publishing `organization.member-removed.v1` (the event record `MemberRemoved` is in Organization.Contracts; nothing sends it yet), private channels and DMs (the read check grows with them), the web client.
- Modules call the publisher after their unit of work has committed and never let a failure reach the caller (Messaging's `AfterCommitLiveEvents`).
