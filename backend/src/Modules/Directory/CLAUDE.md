# Directory (control plane)

Contract: [docs/contracts/phase-1.md](../../../../docs/contracts/phase-1.md) (flows 2 and 3, "Invitation security"). **Human review required** for invitation acceptance.

## Responsibility

- Organization registry and the organization → cell mapping (source of truth for where an organization lives).
- Creating organizations: limited to 5 per account per day; pick a healthy cell for the region (`409 directory.no_cell_available` if none); store the organization `provisioning` and the owner membership `pending`; enqueue `OrganizationProvisioned` in the same transaction; on `Ack` mark both `active`, on a non-retryable `Nack` mark the organization `failed`.
- Membership view per account, fed by versioned `MembershipChanged` (apply only newer versions) and repaired from `MembershipDigest` / `MembershipSnapshot`.
- Invitations:
  - store `InvitationRegistered` as an upsert by `invitation_id`: applied only while `pending` and only for a newer `code_version`, changes `code_hash` and never `status`; `InvitationRevoked` marks it `revoked` (tombstone if unknown, kept until a late registration would be refused anyway; while `accepting` it only sets `revoke_requested_at` and does not override the later `Ack`/`Nack`);
  - `resolve` returns organization name, expiry and `matchesAccount` (no inviter: the control plane never holds the inviter's name), without changing state;
  - `accept`: conditional update `pending` → `accepting` after checking hash, status, expiry, `email_verified = true` and the email match; records `accepted_at` and the account; enqueues `InvitationAccepted` to the organization's mapped cell; idempotent for the same account; `Ack` → `used` and membership active; `Nack` → `failed`;
  - `GET /api/v1/invitations/acceptance` returns the caller's latest acceptance;
  - a scheduled job marks expiry at `expires_at`; `email_hmac` of expired, revoked and failed invitations is deleted after 30 days, of used ones 30 days after use; `accepting_account_id` is cleared when an account is anonymized.
- Endpoints: `GET /api/v1/me/organizations`, `POST /api/v1/organizations`, `GET /api/v1/organizations/{id}`, `POST /api/v1/invitations/resolve`, `POST /api/v1/invitations/accept`, `GET /api/v1/invitations/acceptance`.

## Owns

- Schema `directory`: `organizations`, `memberships`, `invitations`.

## Depends on / provides

- Uses `ICellLinkOutbox` (CellManagement.Contracts) to enqueue downstream messages.
- Implements `ICellMessageHandler<T>` for `MembershipChanged`, `OrganizationUpdated`, `InvitationRegistered`, `InvitationRevoked`, `MembershipDigest`, `MembershipSnapshot`, and `ICellMessageOutcomeHandler<T>` for the `Ack`/`Nack` of `OrganizationProvisioned` and `InvitationAccepted` (both interfaces in CellManagement.Contracts).
- Provides `IDirectoryQueries` (Directory.Contracts): memberships and cells per account, organizations per cell. The upstream scope check is `ICellOrganizationScope` (CellManagement.Contracts), implemented here (`CellOrganizationScope`), so CellManagement does not depend on Directory.

## Rules

- Every upstream message naming an organization is accepted only if that organization maps to the authenticated cell; `cell_id` always comes from the authenticated stream. The link checks organization ids only: handlers look up every other id (`invitation_id`, an account) together with the checked organization, e.g. by `(org_id, invitation_id)`, and snapshot members must name the snapshot's organization.
- Holds no organization content: names, ids, statuses, hashes, and the account data the control plane holds anyway.
- Emails are stored only as HMAC with the control plane's key, over the invitation id (16 bytes, network order) and the address normalized by `EmailAddress` (BuildingBlocks.Domain), the cell's own rule; accept computes it the same way from the account's verified email and the invitation found by its code.
- Invitation codes travel only in request bodies, never in URLs; request body capture is off for `resolve` and `accept`; codes are never logged.
- `resolve` and `accept` are bearer-only and rate limited (10 per account per minute; 1000 per IP per hour, of which at most 100 failed). Unknown, used, revoked and expired codes answer `directory.invitation_invalid` with the same status and body; an email mismatch answers `directory.invitation_email_mismatch` without revealing the address and does not consume the invitation; failures are security log events with ids only.

## Status

- Implemented: tables `organizations` and `memberships`; `GET /api/v1/me/organizations` (active memberships in active organizations, with cell URLs from CellManagement's `ICellCatalog`; at most 500, oldest first) and `GET /api/v1/organizations/{id}` (creator or pending/active member; anyone else gets the same `404 directory.organization_not_found` as for an unknown id).
- Creating organizations (feature flag `Features:OrganizationCreation`; on in the AppHost since the cell creates organizations, off by default elsewhere): `POST /api/v1/organizations` (`OrganizationCreation`) checks name and display name with `DisplayText` (NFC, no control/format/separator/private-use/unassigned characters, user-perceived length) and the region, needs a verified email, takes the account's creation lock without waiting (`pg_try_advisory_xact_lock`; busy → 429) and counts its organizations of the last 24 hours (at most 5), picks the least loaded healthy cell from `ICellCatalog.GetHealthyCellsAsync`, and in one unit of work stores the organization (`provisioning`), the owner's membership (`pending`, version 0) and `OrganizationProvisioned` in the link outbox; `202 { id, status, cellId, cellUrl }`. `OrganizationProvisioningOutcome` (`ICellMessageOutcomeHandler<OrganizationProvisioned>`): `Ack` → organization and owner membership `active`; non-retryable `Nack` → organization `failed` with the code, owner membership `removed`; only for the cell the organization was assigned to. Not yet: an idempotency key for retried creation requests (the daily limit bounds duplicates).
- Invitation registry: table `invitations` (code hash and email HMAC only; a revocation of an unknown invitation leaves a tombstone without them). `InvitationLinkMessages` handles `InvitationRegistered` (validated, then an upsert that applies a newer `code_version` only while `pending` and changes only the hash; a tombstone blocks it) and `InvitationRevoked` (`pending` → `revoked`; `accepting` only records `revoke_requested_at`; terminal states unchanged). Each message takes a transaction advisory lock on the invitation id, then checks that an existing row belongs to the message's organization. Refusals are non-retryable with `directory.invitation_message_invalid`, `directory.invitation_not_in_organization` or `directory.invitation_code_conflict`, and are security log events with ids only. The email HMAC key is `Directory:Invitations:EmailHmacKey` (base64, at least 32 bytes), validated at startup; the AppHost generates a persisted secret. Rotating it would make stored HMACs unmatchable, so a rotation means sending pending invitations again (no key versions yet; accept could also try the old key for the 7-day lifetime). A new invitation is inserted with `ON CONFLICT DO NOTHING`, so two cells racing for one code hash end in a refusal; a resend that loses such a race fails once and is refused on the retry. Checks keep `pending` and `accepting` rows complete, `accepting`/`used` with the accepting account, and `failed` with its code. The control plane does not cap invitations per organization; it relies on the cell's limits (ended invitations stay as rows without their email HMAC; only tombstones are deleted).
- Resolve (feature flag `Features:Invitations`, off by default like the cell's): `POST /api/v1/invitations/resolve` (`InvitationResolution`) hashes a well-formed code (43 base64url characters, SHA-256 over them), finds it by the unique `code_hash` index with its organization, and answers only for a `pending`, unexpired invitation of an `active` organization; `matchesAccount` compares the HMAC of the account's verified email in constant time. `InvitationAttemptFilter` (on the `/api/v1/invitations` group, with a 1 KB body limit and `Cache-Control: no-store`) applies `InvitationAttemptLimits`: sliding windows in memory per instance for 10 attempts per account per minute and 1000 per client network per hour (`ClientNetwork`, BuildingBlocks.Presentation: IPv4 or IPv6 /64), and after 100 failed attempts from a network in an hour refuses its further failures with `429` (its attempts still run, so a valid code works from behind the same NAT); a `404` or `403` counts as failed and is a security log event with the account id only (never the code or the network). Partitions expire with their window; there is no hard cap on their number (accounts are signed in, networks are IPv4 addresses or IPv6 /64s). An `accepting` invitation resolves as invalid, also for the accepting account: the page follows `GET /invitations/acceptance` instead.
- Accept (same flag): `POST /api/v1/invitations/accept` (`InvitationAcceptance`, behind `InvitationAttemptFilter`) finds the invitation by code hash, takes its advisory lock and reads it again by id and hash (a resend may have replaced the code). The same account while `accepting` or `used` gets `202` with that status and nothing changes. Otherwise only a `pending`, unexpired invitation of an `active` organization (else the same `404 directory.invitation_invalid` as resolve); then a verified email (`403 directory.email_not_verified`) whose HMAC matches in constant time (`403 directory.invitation_email_mismatch`, invitation stays pending); both are checked only for a usable code, so they reveal nothing about other codes. In one unit of work: `pending` → `accepting` with `accepting_account_id` and `accepted_at` (microseconds, the same instant as in the message), a `pending` membership if the account has none or a `removed` one (pending and active ones are left alone; `added_membership` records it), and `InvitationAccepted` (normalized verified email, display name by `AccountProfile` with the email as fallback, locale or `en-US`) to `organizations.cell_id`; `202 { organizationId, status }` with `Location: /api/v1/invitations/acceptance`. Lock order: invitation lock, invitation row, membership row, outbox. `InvitationAcceptanceOutcome` (`ICellMessageOutcomeHandler<InvitationAccepted>`, takes the same lock) only for the organization's mapped cell and only while `accepting`, whatever `revoke_requested_at` says: `Ack` → `used` (`used_at`) and a pending or removed membership `active` (the cell added the member, even if the refusal of another acceptance of the same account removed it meanwhile); non-retryable `Nack` or `delivery_expired` → `failed` with the code and the still pending membership `removed` if an acceptance of that account and organization added it and none of theirs is still `accepting`. `GET /api/v1/invitations/acceptance` (same flag, `Cache-Control: no-store`, outside the attempt limits because the page polls it and takes no code) answers the account's newest acceptance `{ organizationId, status, code }` by `invitations_accepting_account_idx`, or `404 directory.invitation_acceptance_not_found`. Security log events (ids only): accepting, refused (email not verified or mismatch), used, failed.
- Invitation jobs (`InvitationJobs`, run by `InvitationJobsWorker` after a random start delay of up to 30 seconds and then every 5 minutes; the host adds it with `AddDirectoryJobs`, tests call the jobs directly; each job's failure is logged and does not stop the other or the worker): expiry marks `pending` invitations with `expires_at <= now` `expired` (acceptance already refuses them from `expires_at`; `accepting` and every other state are left alone), each as a security log event with ids only; retention deletes `email_hmac` of `expired`, `revoked`, `failed` and `used` invitations whose `updated_at` (when they ended or were used: nothing changes them afterwards) is more than 30 days ago, and deletes revocation tombstones (`revoked` without `code_version`) by `revoked_at` after `TombstoneRetention`, 37 days and 1 hour: derived from `InvitationLinkMessages.MaxExpiryAge` and `MaxLifetime`, so a late registration of such an invitation is refused anyway. All use the application clock, as acceptance does. Each statement handles a batch of 250 in its own unit of work, at most 40 batches per job and run, by the partial indexes `invitations_pending_expiry_idx`, `invitations_ended_email_idx` and `invitations_tombstone_idx`; a run goes on while a batch selected a full 250 rows, even if it skipped some. They never wait: rows locked by another transaction are skipped (`FOR UPDATE SKIP LOCKED`, so several instances share the work) and so are invitations whose advisory lock a message or an acceptance holds (`pg_try_advisory_xact_lock`, tried only for the batch), so the lock order of those paths holds and a running acceptance completes. Counts in the run logs and on the spans (`Backroom.Directory`: `invitation expiry`, `invitation retention`).
- Next: the upstream handlers (`MembershipChanged`, `OrganizationUpdated`, digests and snapshots, which must take the invitation lock before membership rows if they touch both); invitations: an organization moved to another cell while an invitation is `accepting` leaves it `accepting` (only the old cell's answer settles it; the 2-minute operations alert catches it) until cell moves exist; clearing `accepting_account_id` when an account is anonymized (it must keep `updated_at` of ended invitations, which the retention counts from); deleting ended rows themselves once past `expires_at` + 30 days + 1 hour (they stay for now for `GET /invitations/acceptance` and diagnostics, without the email HMAC).

- **Contracts** (step 6.3): `Backroom.Modules.Directory.Contracts` with `IDirectoryQueries` (`ListCellsOfAccountAsync`: cells with a pending or active membership; `SelectMembersOfCellAsync`: which of up to 10,000 accounts are members of a cell; `ListOrganizationsOfCellAsync`), implemented by `DirectoryQueries` (one bounded statement each, on the pooled data source).
