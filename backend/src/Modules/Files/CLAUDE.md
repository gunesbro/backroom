# Files (cell)

Contract: [docs/contracts/phase-2.md](../../../../docs/contracts/phase-2.md) (flows 6 and 12, "Data", "HTTP APIs", "Privacy rules"). **Human review required** for every change: access checks, signed URLs and storage credentials.

## Responsibility

- Uploads, completion and signed downloads (step 21). Attachments and deletion (22), malware scanning (23, done), the quota (24), thumbnails and the Files tab (25) and file name search (26) come with their steps.
- `IFileStorage` (Application): the provider interface; `S3FileStorage` (Infrastructure) over any S3-compatible store with the AWS SDK for .NET (SeaweedFS in development and tests, never MinIO). `IFileStorageProvider` chooses the storage per organization; Phase 2 has one per cell.

## Owns

- Schema `files`: `files`, `account_upload_days`, `upload_days` (the upload brakes' daily counters), `outbox` (no events yet; `files.file-deleted.v1` arrives with step 22). Every table has `org_id` and forced RLS.
- The cell's bucket. Keys are `{orgId}/{fileId}`: no name ever appears in a key, URL, log or event.

## Publishes / depends on

- Messaging.Contracts: `IConversationReadAccess` (may the account read, and for now post in, the conversation) and `IMessageFileAccess` (may the account read a message that carries the file; Messaging answers false until step 22).
- Permissions: `files.upload` on upload start (`RequirePermission`).

## Rules

- `POST /api/v1/orgs/{orgId}/files/uploads { conversationId, name, size, contentType }` (`files.upload` and post access): size 1 byte to 100 MB (`413 files.too_large`, `400 files.upload_invalid` below 1), name `FileName` (NFC, trimmed, 1 to 255 code points, no `/` `\`, control or format characters except ZWNJ/ZWJ, not `.`/`..`; `400 files.name_invalid`), content type from `FileTypes` or `application/octet-stream` (no SVG, HTML or parameters; `400 files.type_not_allowed`), unknown or archived conversation `404 files.conversation_not_found`. Writes a `pending` row and answers `201 { fileId, uploadUrl, method: "PUT", headers, expiresAt }`: a presigned PUT valid 15 minutes whose signature covers `Content-Length` (the declared size), `Content-Type` and `If-None-Match: *`, so storage refuses another size or type and any second upload to the key (a completed object can never be replaced through the URL).
- Abuse brakes (`UploadBrakes`, in the start's transaction, before the row is written): per account 30 starts per minute (the newest starts by `files_uploader_created_idx`) and 10 GB per UTC day, per organization 100 GB per UTC day (one counter row per account and day and per organization and day, upserted with a conditional `ON CONFLICT DO UPDATE` whose row lock serializes concurrent starts; account row first, then organization). Declared sizes count at the start; over a limit answers `429 files.rate_limited` with `Retry-After`, and the rollback undoes the counting. Old counter rows are removed by a retention job later (one small row per account and day).
- `POST .../files/{id}/complete` (uploader only, else `404 files.not_found`): no object → `409 files.upload_incomplete` (stays pending); size differs → object deleted, `409 files.upload_incomplete`; the first 512 bytes do not match the declared type (`FileTypes.Confirm`: signature types need their signature, text must have none and no NUL, octet-stream takes the recognised type) → object deleted, `409 files.type_mismatch`. A refused upload stays `pending`, so it can be uploaded again while its URL is valid. Otherwise `scanning` with `detected_type` and `kind` (the response says `scanning`); repeats answer the stored file.
- Malware scan (step 23, `files.file-scan`, worker role, flag `Features:Files`): a maintenance job (ADR 0010; grants in `20261125020000_AddFileScanning`: `SELECT` of `id, org_id, status, storage_key, size, created_at, scan_attempts, scan_next_at`, `UPDATE` of `status, ready_at, scan_attempts, scan_next_at`; partial index on `scan_next_at` of scanning rows). No database connection is held during a scan. Each run (every 10 s, one short transaction) applies the outcomes of finished scans with conditional updates, then claims due files (`FOR UPDATE SKIP LOCKED`, at most 16 queued): `scan_attempts` + 1 and `scan_next_at` moved ahead by a backoff of 5 minutes doubling, so a stuck file never blocks the ones behind it. Claimed files are scanned in the background, 4 at a time (`SemaphoreSlim`), streamed from storage to `IFileScanner` (`ClamAvScanner`: clamd `INSTREAM` over TCP, own implementation, 64 KiB chunks, never buffered whole; exact `stream: OK` / `stream: {name} FOUND` each ended by NUL, anything else, a truncated reply or a size that differs from the recorded one is `ScannerUnavailableException`; `Files:Scanner` `Host`, `Port`, `ConnectTimeout` 5 s, `ScanTimeout` 45 s, validated at startup). Clean: `ready`. Infected, object missing, or no answer after 5 attempts (the 6th claim gives up): `rejected` and the object deleted. When the scanner cannot be reached (`IsOutage`) the attempt is given back and claiming pauses 30 s: an outage never rejects files; they stay `scanning` and unserved. Outcomes wait in memory for the next run; a lost one is a retry after the backoff. clamd must run with `AlertExceedsMax` and `AlertEncrypted` (content over its limits is reported as found, never clean) and limits of at least 100 MB. Downloads: the uploader of a `scanning` file gets `409 files.scan_pending`; everyone else `404`. Rejection notice: the update that rejects a file returns `org_id` and the uploader (`SELECT` of `uploader_account_id` is granted by `20261125120000_GrantUploaderToScanJob`; never the name or type), and the job stages a `FileRejectedPayload` (ids and reason `malware` or `scan_failed`). At the start of the next run it keeps only the staged files the database shows as `rejected` (a rolled-back transaction leaves none) and publishes those through `ILiveEventPublisher` from a background task (a slow backplane never holds the transaction), so only the uploader's account group gets `FileRejected`; best effort, the file stays `rejected` either way. Logs carry ids only.
- `GET .../files/{id}/download`: access is checked on every request. A `ready` file: only its uploader, while they can still read its conversation; an `attached` one: `IMessageFileAccess`. Every other state (rejected, deleted, expired), refusal and unknown answer `404 files.not_found`. Success is `302` to a signed GET valid 60 seconds with `response-content-disposition=attachment` and the detected type, plus `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`; the redirect is written by `SignedUrlRedirect`, never `TypedResults.Redirect` (that logs the URL). A signed URL already handed out stays valid until it expires (at most 60 seconds); revocation applies to the next request.
- Storage settings `Files:Storage` (`S3StorageOptions`, validated at startup): `ServiceUrl`, optional `PublicUrl` (the host clients reach; signatures name it), `Bucket`, `AccessKeyId`, `SecretAccessKey`, `Region`, `Timeout` (5 s per attempt), `MaxRetries` (1); https outside Development; `CreateBucket` only in Development. The SDK sends through `IHttpClientFactory` (`Backroom.Files.Storage`) without the hosts' default resilience handler (the SDK retries itself), with checksums only where required. Completion holds the unit of work's connection during its storage calls, so they share a 15-second budget (`CompletionStorageBudget`); a slow store fails the request instead of starving the pool.
- Only this module's Infrastructure may use an object storage SDK (architecture test `ObjectStorageUsageTests`).

## Status

- Implemented (Phase 2 step 21, behind `Features:Files`, app role only): schema `files` (migration `20261124150000_CreateFiles`), upload start, completion and download, `S3FileStorage`, the AppHost's SeaweedFS with generated secret credentials and one bucket per cell (`backroom-cell-{id}`).
- Implemented (Phase 2 step 23, behind `Features:Files`): the scan above, `IFileStorage.ReadAsync`, the AppHost's ClamAV container (`clamav/clamav:1.5.4` pinned by digest `sha256:7054e3f3...c214e` too, port 3310 published on 127.0.0.1 only, signature volume, `CLAMD_CONF_StreamMaxLength=100M`, `AlertExceedsMax`, `AlertEncrypted`) and the worker's storage and scanner settings; tests use `ClamAvServer` (same image, offline, EICAR signature only).
- Known limitation: the object is deleted before the runner commits the rejection; if that transaction rolls back, the outcome is lost, the file is claimed again after its backoff and rejected as missing (`scan_failed` instead of `malware`). The file is never served meanwhile. Moving the deletion after the commit needs an after-commit hook in the maintenance runner.
- Not yet from step 23: a durable path for the rejection notice (no outbox event; the live hint is enough while the uploader can also read the file state). Also not yet: the production scanner (deploy phase) and signature freshness monitoring.
- Not yet: the quota reservation (step 24 plugs in before the row is written in `FileService.StartAsync`), the 24-hour expiry of unattached uploads, browser CORS on the store for direct uploads from the web app, `X-Content-Type-Options` on the store's own responses (deploy-phase store config or proxy), one storage identity per bucket in deployments (development shares one SeaweedFS identity between the cells; the deploy checklist must require one per bucket), and a file name on downloads (the URL must not carry it; the client names the saved file).
