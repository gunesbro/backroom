# ControlPlaneConnector (cell)

Contract: [docs/contracts/phase-1.md](../../../../docs/contracts/phase-1.md) ("Cell ↔ control plane link"), protocol [cell_link.proto](../../../proto/backroom/controlplane/v1/cell_link.proto). Technical module (no Domain or Presentation project). **Human review required** for key handling and authentication.

## Responsibility

- Runs in the `worker` role. A PostgreSQL advisory lock ensures one worker holds the stream.
- Gets the cell's short-lived token from Keycloak (`client_credentials` + client assertion signed by the cell's private key) and reconnects with a fresh token before the current one expires.
- Opens the stream, sends `Hello`, resends every unacknowledged upstream message, sends `Heartbeat` every 30 s; HTTP/2 PING liveness; exponential backoff with jitter.
- Downstream handling: de-duplicate by `message_id` in the inbox, call the owning module through its contract **in the same transaction** as the inbox row, commit, then `Ack`; answer business rejections with a non-retryable `Nack`, unknown types with `unsupported_type`.
  - `OrganizationProvisioned` → `IOrganizationProvisioning` (Organization.Contracts)
  - `InvitationAccepted` → `IInvitationAcceptance` (Organization.Contracts)
  - `SessionRevoked` → `ISessionRevocation` (Realtime.Contracts)
  - `MembershipSnapshotRequested` → `IMembershipQueries` (Organization.Contracts) → upstream `MembershipSnapshot`
- Upstream: consumes `organization.member-added.v1` / `member-removed.v1` → `MembershipChanged` (with version), `organization.invitation-created.v1` → `InvitationRegistered` (code hash from `IInvitationLinks`, with `code_version`; when that version is acknowledged, calls `IInvitationRegistration.MarkRegisteredAsync(invitationId, codeVersion)`), `organization.invitation-revoked.v1` → `InvitationRevoked`, all through its own outbox.
- Every 15 minutes: `FullSync` (repair revoked sessions; alert on unknown organizations, never delete) and `MembershipDigest`.

## Owns

- Schema `control_plane_connector`: `link_inbox` and `outbox` (link delivery), `inbox` (integration events, organization-scoped with RLS), `cell_epoch` (the cell's epoch and its confirmation). (Deviation from the module plan's "no persistent data": the delivery guarantee needs it.)
- The cell's private key in the cell's secret store (development: user secrets). It never leaves the cell.

## Rules

- The only module that talks to the control plane.
- Never sends organization content upstream.

## Status

- Implemented: registration on the worker's first start (`CellRegistrationWorker`), the key store (`cell-key.pem` and a `registered` marker in the key directory; default `%APPDATA%/Backroom/cells/{cellId}`; the AppHost sets `ControlPlaneConnector:KeyDirectory` to `%APPDATA%/Backroom/dev/{apphost-id}/cells/{cellId}`, where the id is the path hash its Docker volumes carry, so checkouts and worktrees never share a marker), and access tokens with a client assertion signed by the cell's key (`CellCredentials`).
- The key directory is restricted to the cell's user (Unix mode 0700; on Windows a protected ACL for the current user only). All worker instances of a cell must share one key directory: a second key would fail registration, because a registration key is bound to the first public key that claims it.
- Drift between the local marker and the control plane (`Health/CellLinkStatus`, health check `control-plane-link`): a `PermissionDenied` link, Keycloak refusing the cell's credentials (400/401), or a 4xx registration refusal (not 408/429) is logged as a `Security:` error with the cell id and status only and makes `/health` unhealthy; the workers keep backing off, so a repair takes effect without a restart, and the state clears at the next `Welcome` or registration. The cell never re-registers on its own (registration keys are single-use and bound to the first key). Keycloak's 400 `invalid_client` also covers a client assertion refused for clock skew, which its error description does not reliably tell apart; that state is reported the same way and clears at the next `Welcome` once the clock is right.
- Outside Development, `ControlPlaneUrl` must use https; a cell that is not registered and lacks the registration key or URL stops at start.
- Link worker (`CellLinkWorker`): after registration and with the lease (PostgreSQL advisory lock on a dedicated connection, released explicitly; checked before every heartbeat), connects with the cell's token, sends `Hello`, waits 10 s for `Welcome`, sends `Heartbeat` every 30 s, renews the stream 60 s before the token expires, retries with exponential backoff and full jitter (1–60 s); HTTP/2 keep-alive pings every 20 s; 4 MB message limit. Downstream durable messages get a retryable `Nack` `link.not_ready` until their handlers exist. Development: the control plane's https endpoint (gRPC needs HTTP/2).
- Link delivery (schema `control_plane_connector`, not organization-scoped, migrated in every role): the tables span organizations, so instead of RLS the application role may only `INSERT` (`ON CONFLICT DO NOTHING` without a target); reading and settling run as the relay role (`OutboxRelay:ConnectionString`), which only the worker gets. `UpstreamOutbox.EnqueueAsync` writes `outbox` in the caller's unit of work with the trace context (only the connector's own consumers use it). The worker takes due messages every second (at most 8 MB of payloads per batch); a new stream sends one message (the least-tried one, so a message that broke earlier streams does not go first) and opens the window of 100 unanswered at its first answer. An answer overdue after 30 s, a retryable `Nack`, or a stream that broke while the message was the oldest unanswered one counts an attempt and delays the next send (2 s doubling to 5 min), so a message that always breaks the stream expires alone; `Ack` / non-retryable `Nack` settle and delete the payload; after 50 attempts `delivery_expired` (logged as an error with the message type); an unparsable payload `invalid_payload`. Only a stream the control plane ended charges the oldest unanswered message; the cell's own failures (database, lease) charge nothing. Streams must outlive the 30 s answer timeout (token lifetime above 90 s; the realm uses 300 s): renewal charges nothing, so with shorter streams a never-answered message would be resent forever. The relay pool has 2 connections; trace context is stored only if well-formed (tracestate at most 512 characters). Downstream: `DownstreamReceiver` opens a `cell-link receive` span linked to the sender's trace, enters the message's organization (`OrganizationProvisioned`, `InvitationAccepted`, `MembershipSnapshotRequested`), checks for a handler without constructing it, records the id in `link_inbox` and runs `IDownstreamHandler<T>` in one unit of work, then `Ack`; `LinkMessageRejectedException` → non-retryable `Nack`; `LinkPrerequisiteMissingException` → retryable `Nack` with its code (logged as a warning, type only); other failures → retryable `processing_failed`; no handler → retryable `link.not_ready`. Handlers run inline in the read loop, so they must finish well under 30 s (or answers to upstream messages turn overdue). A database error while sending or settling ends the stream (reconnect with backoff; every pending message is sent again).
- Downstream handlers: `OrganizationProvisioned` → `IOrganizationProvisioning` (rejections become a non-retryable `Nack` with Organization's code). `InvitationAccepted` → `IInvitationAcceptance` (`InvitationAcceptedHandler`): unparsable invitation or account ids or a missing or out-of-range `accepted_at` → non-retryable `organization.invitation_acceptance_invalid`; Organization's `NotFound` (an invitation or organization the cell does not know yet) → retryable `Nack` `organization.invitation_not_found`, so it is retried with backoff until it exists or expires after 50 attempts; every other failure → non-retryable `Nack` with Organization's code.
- Invitation registration: `InvitationCreatedConsumer` reads the hash of the event's code version through `IInvitationLinks.GetCodeHashAsync` and enqueues `InvitationRegistered` (nothing if a resend replaced the version or the invitation is no longer pending); `InvitationRevokedConsumer` always enqueues `InvitationRevoked` (the control plane keeps a tombstone). Both run in the worker's RabbitMQ consumers, in the event's organization, with the standard `inbox`. Outcome hook (`UpstreamOutcomes`): when `InvitationRegistered` is acknowledged, the worker calls `IInvitationRegistration.MarkRegisteredAsync` in the invitation's organization *before* settling; a failure (lock timeout, database) counts an attempt and sends the message again instead of settling, so the email is never lost; `false` from the call is settled normally. Only the outcome's ids are kept in memory per message in flight. The link's own inbox is `link_inbox` (renamed in `AddEventInbox`).
- Next: the `MembershipSnapshotRequested` handler (a missing prerequisite throws `LinkPrerequisiteMissingException`); the membership event consumers; the `state` table; the organization part of FullSync (alert on unknown organizations); retention of `link_inbox` and settled `outbox` rows (the relay already cleans the event `inbox`).

- **Revoked sessions** (step 6.3): `SessionRevokedHandler` (`IDownstreamHandler<SessionRevoked>`) validates the message (account id, session id at most 128 characters, both dates, `keep_until` not before `revoked_at`; otherwise non-retryable `Nack` `realtime.session_revocation_invalid`) and calls `ISessionRevocation.RevokeAsync`; a failure of Valkey is an ordinary exception, so the answer is a retryable `Nack` `processing_failed` and the control plane sends it again. `FullSyncRunner` runs as a fourth loop of the stream (`CellLinkWorker`): once right after `Welcome` and then every `Welcome.full_sync_interval_seconds` (a value outside 60 s to 1 day falls back to 15 minutes), with the stream's token, applying each revocation of the answer through the same contract; a failed run is logged and tried again at the next interval, and never ends the stream.

- **Cell epoch** (Phase 2 step 4, docs/adr/0011 "Cell epoch"; _human review_): `cell_epoch (cell_id, epoch, confirmed, updated_at)`, one row per cell id; the app role may only `SELECT`, the relay role writes it (`CellEpochStore`). After `Welcome` the worker stores `Welcome.epoch` confirmed (0 confirms nothing); when the control plane ends the stream with `FAILED_PRECONDITION` `cell.epoch_changed` it clears the confirmation (no attempt charged), then reconnects with the usual backoff. Write fence (`AddCellEpochFence` / `UseCellEpochFence`, app role only, after authorization): every method other than GET, HEAD, OPTIONS and TRACE, except the hub path, answers `503 cell.epoch_unconfirmed` with `Retry-After: 5` and `no-store` while the cell has no confirmed row. The app role learns the state from the cell's PostgreSQL, not Valkey: the confirmation must travel with the database that a restore replaces (the runbook clears it there), the app already depends on that database for every write, and the table is read-only for the app role. `CellEpochGate` (the cell's `ICellWriteFence`, BuildingBlocks) keeps the answer 2 s, runs one lookup at a time and fails closed when the lookup fails. In the worker the same fence holds the integration-event consumers (a delivery is neither handled nor acknowledged; it is requeued after 5 s) and skips maintenance runs; downstream link messages are handled only after `Welcome`, so after the confirmation. An interrupted confirmation is cleared again (`ConfirmEpochAsync`). Memberships are not reconciled after a restore (open question, see the runbook).
